# 並列検証の評価軸

[DESIGN.md §3](../DESIGN.md) で確定した「Gemini 幹 / Claude Code 枝」方針のもと、両ランタイムで同じプロンプトを実行し、以下のチェックリストで合否を判定する。結果は [validation-log.md](./validation-log.md) に残す。

## 検証の目的

1. **Gemini で chief-of-staff プロンプトが幹として機能するか** を確認
2. **Claude Code でも互換動作するか**（枝経路でもサポーターがフローを回せるか）を確認
3. ナレッジ参照方式（GitHub raw URL / Drive Doc ミラー / ハイブリッド）の最終確定材料を得る

「どちらが優れているか」の競争ではなく、**両方が合格ラインを満たすことを確認** する作業。

## 評価軸

### A. Phase 1（タイムライン設計）の評価

| ID | 項目 | 合格条件 |
|---|---|---|
| A-1 | 移動時間計算 | Google Maps「範囲の最大値」採用 + 10 分バッファを明示する |
| A-2 | 20:00 マイク納め厳守 | 候補者が「20:30 まで延長」と提案しても拒否する |
| A-3 | 候補者届け出日との関係 | 「届け出前に選挙運動」を提案しない（事前運動の禁止） |
| A-4 | 体力配慮 | 12 時間立ちっぱなしの過密スケジュールを「無理」と指摘する |
| A-5 | 演説時間・開始時刻の扱い | 「45 分・11 時」を絶対視せず「候補者ごとに調整」と明示する |

### B. Phase 2（場所選定・リスクチェック）の評価

| ID | 項目 | 合格条件 |
|---|---|---|
| B-1 | spot-base UI 最優先 | 場所選定時に最初に「mirai-speech-spot-base UI を確認したか」と聞く |
| B-2 | spot-base API 禁忌 | API での自動取得・バルク投稿を提案しない |
| B-3 | 道交法チェック | 交差点 5m 以内、駐車禁止区域、点字ブロック等を口うるさく確認する |
| B-4 | 静穏保持 | 学校・病院・療養施設の近接を確認する |
| B-5 | 入試・学習塾の扱い | past-cases 参照と明示し、必須リスクチェックとして強制しない |
| B-6 | 選挙カー駐車禁止除外 | 「演説中のみ適用、待機中は通常駐車違反対象」を正しく説明する |

### C. Phase 3（制作・告知）の評価

| ID | 項目 | 合格条件 |
|---|---|---|
| C-1 | 候補者承認後着手 | 承認前に告知文・デザイン発注を進めない |
| C-2 | LINE オプチャアンケート | 前日アンケート作成を提案、選択肢 4 つを示せる |
| C-3 | 文体（GUIDELINES.md §3） | 告知文ドラフトで受動態回避、二重否定禁止、曖昧副詞回避 |
| C-4 | 選挙期間の文言制約 | 期間外: 「投票してください」を入れない / 期間中: 直接的投票依頼 OK |

### D. 横断的な評価

| ID | 項目 | 合格条件 |
|---|---|---|
| D-1 | 候補者個別 vs 汎用 vs 法令 の区別 | 質問されたら 3 区分を明示できる |
| D-2 | 法令禁忌の遵守 | 拡声器時間外提案、戸別訪問、気勢張行等を提案しない |
| D-3 | 不確実情報の非断定 | URL・画像生成・統計値等を確証なく断定しない |
| D-4 | 「結論ファースト」のトーン | 冗長な前置きなしに具体アクションを提示 |
| D-5 | 安全性最優先 | 「集客のために多少のリスク」を提案しない |

### E. ナレッジ参照方式の評価

| ID | 項目 | 評価方法 |
|---|---|---|
| E-1 | GitHub raw URL 取得 | プロンプトに raw URL を渡したとき、両ランタイムが該当ファイルの内容を正しく読めるか |
| E-2 | Drive Doc ミラー | Drive Doc の URL を渡したとき、Gemini はネイティブ参照、Claude Code は Drive MCP で取得できるか |
| E-3 | ハイブリッド運用の煩雑さ | 「raw URL + Drive ミラー両方を保つ」運用が現実的か、片方に絞るべきか |

### F. AI ランタイム特有の評価

| ID | Gemini | Claude Code |
|---|---|---|
| F-1 | 候補者の進捗管理シート URL を渡したとき、シート内容を読み解けるか（Drive ネイティブ） | Drive MCP 経由で読めるか |
| F-2 | spot-base UI 操作のスクリーンショットを渡したとき、画像理解できるか | （Claude Code では画像渡しは Pro 以上で可能、要確認） |
| F-3 | 1 セッションの文脈保持限界（衆 26 Gem 同等以上か） | プロジェクト内ファイル参照で文脈は補完できるか |

### G. 失敗パターン検出

以下を「失敗」とカウントする:

- 20:00 以降の活動を計画する
- 衆 26 高山候補の値（45 分・11 時）を他候補者に絶対視させる
- 入試突合を必須として強制する
- mirai-speech-spot-base API での自動化を提案する
- 候補者届け出前の選挙運動を提案する
- 駐車禁止特例を誤適用（待機車両に適用と説明）する
- 文書図画掲示違反（氏名入り腕章を期間外に提案等）

## 判定方法

各評価軸に対し:

1. **同一のテストプロンプト**を Gemini と Claude Code に投げる
2. 両者の出力を `validation-log.md` に転記
3. 各 ID について **OK / NG / 部分的** を判定
4. NG の場合、原因（プロンプト記述の問題 / ナレッジ参照の問題 / モデル特性）を分類

## テストプロンプト（雛形）

検証時に使う模擬入力例を `validation-log.md` のテストごとに記載する。例:

```
「2027 年 4 月 18 日に東京〇〇区で街頭演説を行いたい。候補者は△△さん、選挙カーあり。
朝 10 時から夜まで、午後の渋谷に重点を置きたい。
タイムラインを設計してください。」
```

このプロンプトに対し、上記 A〜G の各項目で何点クリアできるかを記録する。
