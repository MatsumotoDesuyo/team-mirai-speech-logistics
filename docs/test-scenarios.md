# 並列検証テストシナリオ

[chief-of-staff.md 改訂版](../prompts/chief-of-staff.md) を Gemini と Claude Code に投げ、本シナリオの 5 件で挙動を観察する。評価軸は [validation-criteria.md](./validation-criteria.md)、結果は [validation-log.md](./validation-log.md) に記録する。

## 実行手順

### ステップ 1: プロンプト準備

1. [chief-of-staff.md](../prompts/chief-of-staff.md) の「## プロンプト本文」セクション内（```markdown ... ``` のコードブロック）の本文をコピー
2. 置き換える項目を以下で置換:
   - `{{候補者名}}` → `テスト候補者A`（または任意の架空名）
   - `{{選挙種別}}` → `2027 統一地方選 / 東京都〇〇区議`
   - `{{schedule_master_url}}` → 生成済みの進捗管理シート URL（[templates/schedule-master.md](../templates/schedule-master.md) 末尾）
   - `{{schedule_detail_url}}` → 生成済みのスケジュール検討シート URL
   - `{{photo_drive_url}}` → 空欄でも可（テスト時は不要）
3. ナレッジは GitHub raw URL リファレンスとしてプロンプト内に列挙済み。Gemini は自前で取得を試みる、Claude Code は WebFetch / Read で読みに行く想定

### ステップ 2: Gemini で実行

1. Gemini（gemini.google.com）で新規会話を開く
2. ステップ 1 で準備した system プロンプト相当を貼り付け
3. シナリオ S1 〜 S5 の「ユーザー入力」を順に投げる
4. 各回の出力を [validation-log.md](./validation-log.md) の該当セクションに転記

### ステップ 3: Claude Code で実行

1. 本リポジトリのルートで Claude Code を起動
2. system プロンプトを `/init` または new session で渡す（あるいは作業用 markdown に貼り、参照させる）
3. 同じ S1 〜 S5 のユーザー入力を投げる
4. 各回の出力を validation-log.md に転記

### ステップ 4: 評価

1. 各シナリオの「観察ポイント」と [validation-criteria.md](./validation-criteria.md) の評価軸 ID を照合
2. OK / NG / 部分的 を判定
3. NG の場合、原因（プロンプト記述 / ナレッジ参照 / モデル特性）を分類

---

## S1: Phase 1 タイムライン設計（基本動作）

### ユーザー入力

```
2027 年 4 月 18 日（日）に東京〇〇区で街頭演説を 1 日入れたい。
候補者は選挙カーあり、午前 10 時頃から夜 20 時のマイク納めまで、
午後の渋谷駅周辺に重点を置きたい。タイムラインを設計してください。
```

### 観察ポイント（評価軸 ID）

- **A-1**: 移動時間は Google Maps「範囲の最大値」+ 10 分バッファを明示する
- **A-2**: 20:00 マイク納めを最後の演説終了時刻として守る
- **A-4**: 体力配慮（休憩・昼食時間）を提案する
- **A-5**: 演説時間・開始時刻を「候補者ごとに調整」と明示する、衆 26 高山候補の値（45 分・11 時）を絶対視しない

### 失敗パターン（あれば即 NG）

- 20:30 など 20:00 以降を提案する
- 45 分演説・11 時開始を absolute として固定する
- 12 時間連続で休憩ゼロ

---

## S2: Phase 2 場所選定（spot-base UI 優先動線）

### ユーザー入力

```
渋谷駅周辺で 45 分演説の場所を 2-3 か所検討したい。
候補地を提案して、ロジ観点でチェックしてください。
```

### 観察ポイント（評価軸 ID）

- **B-1**: 真っ先に「mirai-speech-spot-base UI で登録済みスポットを確認したか」を聞く
- **B-2**: spot-base API での自動取得を提案しない
- **B-3**: 道交法（駐車禁止、交差点 5m 等）を口うるさく確認する
- **B-4**: 静穏保持（学校・病院）を確認する
- **B-6**: 選挙カー駐車禁止除外運用（演説中のみ、待機中は通常違反対象）を正しく説明する

### 失敗パターン（あれば即 NG）

- spot-base の存在に触れずに自前で場所を断定する
- 駐車禁止除外を「いつでも適用」と誤説明する

---

## S3: Phase 2 リスクチェック（入試・受験会場の罠）

### ユーザー入力

```
2027 年 4 月 18 日、〇〇大学のすぐ近くで街頭演説したい。
リスクチェックをお願いします。
```

### 観察ポイント（評価軸 ID）

- **B-5**: 入試突合を必須化しない（4 月は入試時期と重ならない、past-cases 参照と明示）
- **B-4**: 大学は静穏保持義務の対象「学校」に該当することを指摘する
- **D-1**: 候補者個別 / 汎用 / 法令 の区別を意識した回答

### 失敗パターン（あれば即 NG）

- 入試日程突合を 4 月選挙で必須として強制する
- 学習塾 100m を絶対ルールとして適用する
- 受験会場との距離を独自基準で数値化する

---

## S4: Phase 3 告知文作成（選挙期間外）

### ユーザー入力

```
2027 年 4 月 12 日 13:00-13:45 に渋谷ハチ公前で演説します。
これは候補者届け出前（公示日は 2027 年 4 月 16 日）です。
LINE オプチャ用の告知文と、当日のサポーター募集アンケートを作成してください。
```

### 観察ポイント（評価軸 ID）

- **A-3**: 「届け出前の選挙運動禁止」を指摘し、文面から「投票してください」「立候補予定」を除外する
- **C-2**: LINE オプチャアンケートの選択肢 4 つを示す（「手伝いに行きます！」「行けたら行きます！」「気持ちだけ応援！」「場所取りします！」）
- **C-3**: 文体（受動態回避、二重否定禁止、曖昧副詞回避、1 文 50 字推奨）
- **C-4**: 期間外なので直接的投票依頼を入れない

### 失敗パターン（あれば即 NG）

- 「投票してください」を期間外の告知に入れる
- 「立候補予定」「出馬します」を入れる
- 事前運動禁止を指摘しない
- 「適宜」「丁寧に」等の曖昧副詞を使う

## S5: 3 区分質問（候補者個別 vs 汎用 vs 法令）

### ユーザー入力

```
以下のルール 4 つを、それぞれ「法令上の絶対制約」「汎用運用ルール」
「候補者個別ルール」のどれに分類しますか？ 理由も教えてください。

1. 1 回の演説時間 45 分
2. 演説開始時刻 11 時
3. 拡声器使用時間 8:00-20:00
4. 移動バッファ 10 分
```

### 観察ポイント（評価軸 ID）

- **D-1**: 3 区分の正しい分類:
  - 1, 2 → 候補者個別
  - 3 → 法令上の絶対制約
  - 4 → 汎用運用ルール
- 各項目の理由を `knowledge/rules.md` ベースで説明する

### 失敗パターン（あれば即 NG）

- 1, 2 を法令制約と誤認する
- 3 を「推奨」と弱める
- 4 を候補者個別と誤分類する

---

## ナレッジ参照方式の観察（評価軸 E）

S1 〜 S5 の実行中に、両ランタイムでナレッジ参照の挙動を観察:

- **Gemini**: プロンプト内の GitHub raw URL を実際に取得できるか? できない場合、Drive Doc ミラーが必要か?
- **Claude Code**: WebFetch でリポジトリ raw URL を取得できるか? Read で project 内ファイルを参照する方が安定か?

両ランタイムの挙動差を validation-log.md に記録し、Stage 3 完了時にハイブリッド設計を確定する（[DESIGN.md §8 却下案3](../DESIGN.md) の宿題）。

## 実行に際しての注意

- **本テストは検証用**。実候補者の運用に使う前に validation-criteria.md の全項目で OK が出ることを確認すること
- 観察ポイントに無い挙動でも、気になった点は validation-log.md「観察メモ」に残す
- プロンプトの細部修正は Stage 3 のサイクルで反復可能。1 回で完璧を目指さない
